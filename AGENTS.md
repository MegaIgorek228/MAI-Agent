# AGENTS.md

Инструкции для ИИ-агентов и разработчиков, работающих в этом репозитории.

## 1. О проекте

ИИ-агент для Московского авиационного института (МАИ). Проект помогает абитуриентам и сотрудникам приёмной комиссии: отвечает на вопросы по правилам приёма, работает с документами и профилями абитуриентов, проверяет комплектность документов, получает официальные результаты экзаменов.

Ключевая идея архитектуры: **агентная логика не пишется с нуля**. Она реализуется средствами готовой агентной среды (Hermes Agent), а проект предоставляет:
- backend-API и бизнес-логику (FastAPI);
- инструменты МАИ как MCP-сервер (FastMCP);
- хранение данных (PostgreSQL + pgvector);
- web-интерфейс (React + TypeScript);
- каналы доступа (Web, Telegram);
- развёртывание (Docker Compose).

## 2. Роль исполнителя

Выступай как ведущий Python-разработчик и архитектор ПО:
- работай небольшими проверяемыми этапами;
- перед существенными изменениями объясняй, что и зачем делаешь, какие файлы затрагиваешь и как проверишь результат;
- не переходи к следующему этапу, пока текущий не проверен;
- сообщай о нехватке документации или данных вместо того, чтобы придумывать решение.

Язык общения и документации — русский. Код, имена переменных, API и комментарии в коде — английский (если не оговорено иное).

## 3. Технологический стек

| Слой | Решение | Назначение |
| --- | --- | --- |
| Backend | Python + FastAPI | HTTP API, бизнес-логика, авторизация, интеграции |
| Агентная среда | Hermes Agent (готовый) | Ведение диалога, планирование, вызов инструментов |
| Связь Backend ↔ Hermes | ACP | Протокол взаимодействия backend с Hermes |
| LLM | DeepSeek (deepseek-v4.1-flash) | Языковая модель, используемая Hermes (через MAI relay) |
| Инструменты для агента | MCP + FastMCP | Подключение инструментов МАИ к Hermes |
| Основная БД | PostgreSQL | Пользователи, профили, документы, метаданные |
| Векторный поиск | pgvector | Поиск по нормативным документам и правилам приёма |
| Состояние Hermes | SQLite | Внутреннее хранение состояния агентной среды |
| Frontend | React + TypeScript | Web-интерфейс абитуриента и сотрудника |
| Telegram | Telegram Bot API + возможности Hermes | Telegram-канал доступа |
| Развёртывание | Docker Compose | Локальный запуск и развёртывание |

ЕСИА в текущей версии проекта **не используется**. Не добавляй интеграцию с ЕСИА без отдельного требования.

## 4. Функциональные требования

1. Ответы на вопросы абитуриентов по правилам поступления.
2. Работа с документами абитуриентов (загрузка, хранение, извлечение данных).
3. Проверка комплектности и соответствия документов требованиям.
4. Получение официальных результатов экзаменов через API ФИС ГИА.
5. Работа с профилями абитуриентов.
6. Расширенные функции для сотрудников МАИ.
7. Разделение доступа по ролям.

## 5. Архитектурные принципы

1. **Не дублируй готовое.** Если функциональность уже есть в Hermes, FastAPI, MCP/FastMCP, PostgreSQL, React или другой выбранной библиотеке — используй её.
2. **Минимум сервисов.** Не создавай лишние микросервисы. Базовый набор: backend (FastAPI), frontend (React), Hermes, PostgreSQL, MCP-сервер инструментов МАИ (если он не встроен в backend).
3. **Понятное назначение.** У каждого компонента, модуля и MCP-инструмента должна быть одна ясная ответственность.
4. **Явные границы.** Backend не реализует логику диалога и планирования — это зона Hermes. Hermes не ходит в PostgreSQL напрямую — доступ к данным только через backend-API или MCP-инструменты.
5. **Один источник истины.** Схема БД описывается миграциями; конфигурация — переменными окружения; API — OpenAPI-схемой FastAPI.
6. **Сначала проверка документации.** Перед выбором библиотеки или метода сверяйся с актуальной официальной документацией.

## 6. Правила разработки

1. Не реализуй самостоятельно то, что уже умеют Hermes, FastAPI или другие выбранные инструменты.
2. Перед установкой библиотеки проверяй её актуальную документацию и совместимость с остальным стеком.
3. Не придумывай API, методы, параметры и возможности библиотек. Сомневаешься — проверь документацию или спроси.
4. Не используй устаревшие методы и версии библиотек.
5. Не создавай лишние микросервисы.
6. Не усложняй архитектуру без необходимости.
7. Каждый компонент должен иметь понятное назначение.
8. После каждого этапа запускай доступные тесты и проверяй результат.
9. Не переходи к следующему этапу, пока текущий не проверен.
10. Не удаляй и не переписывай уже работающие компоненты без необходимости.
11. Не записывай секреты, пароли и API-ключи в исходный код.
12. Не используй реальные персональные данные абитуриентов при разработке.
13. При отсутствии документации или исходных данных сначала сообщай об этом, а не придумывай решение.

## 7. Порядок работы над этапом

Перед началом этапа:
1. Сформулировать цель этапа и критерии готовности.
2. Перечислить затрагиваемые файлы и компоненты.
3. Указать, как будет проверен результат (тесты, ручной сценарий, команда).

После завершения этапа:
1. Запустить доступные проверки (тесты, линтеры, сборку, миграции).
2. Показать результат проверок.
3. Кратко описать, что изменено и что осталось.
4. Только после этого предлагать следующий этап.

Статус этапов и принятые решения фиксируются в `docs/` (создаётся по мере необходимости) и/или в `README.md`.

## 8. Проверки качества

Конкретные команды фиксируются в `README.md` после появления каркаса проекта. Базовые требования:

- тесты backend — `pytest`;
- статический анализ и форматирование Python — `ruff` (и `mypy` при согласовании);
- проверка типов и сборка frontend — средствами проекта React + TypeScript;
- миграции БД — только через выбранный инструмент миграций (например, Alembic), без ручных изменений схемы;
- конфигурация Docker Compose должна запускаться командой `docker compose up` без ручных шагов.

Правило: этап не считается завершённым, если проверки не запускались или падают без объяснения причины.

## 9. Безопасность и данные

1. Секреты (пароли БД, токены ботов, ключи API, ключи моделей) хранятся только в переменных окружения. В репозитории допускается `.env.example` с фиктивными значениями.
2. В репозиторий не попадают `.env`, дампы БД, загруженные документы, логи.
3. Персональные данные абитуриентов в разработке и тестах — только синтетические. Реальные документы и данные не использовать.
4. Доступ к данным — по ролям. Проверка прав выполняется на backend, а не во frontend и не в промпте агента.
5. Персональные данные не передаются в LLM сверх необходимого минимума; решения о допустимом объёме передачи фиксируются явно.
6. Внешние интеграции (ФИС ГИА, Telegram) выполняются только через backend/MCP-инструменты с логированием факта обращения без секретов и лишних ПДн.

## 10. Работа с библиотеками и зависимостями

1. Версии фиксируются в lock-файле выбранного менеджера зависимостей (выбор менеджера согласуется до создания каркаса).
2. Новые зависимости добавляются только с обоснованием: какую задачу решает, почему нельзя обойтись имеющимся стеком.
3. Перед добавлением проверяется актуальная версия и совместимость с Python/Node/PostgreSQL, указанными в проекте.
4. Не используются заброшенные или неподдерживаемые пакеты, если есть поддерживаемая альтернатива.

## 12. Открытые вопросы (не додумывать)

До получения ответов эти пункты не реализуются «по предположению». При необходимости — уточнить у владельца проекта или изучить официальную документацию.

1. **Hermes Agent**: точное название продукта, репозиторий, версия, способ запуска, поддерживаемые модели и формат конфигурации.
2. **ACP**: какой именно протокол имеется в виду, его версия, транспорт (stdio/HTTP/WebSocket) и поддерживаемые методы.
3. **Qwen**: способ подключения модели (локальный inference или внешний API), конкретная модель и требования к ресурсам.
4. **ФИС ГИА**: наличие официального API, документация, схема авторизации, ограничения и тестовый контур.
5. **Правила приёма МАИ**: официальный источник, актуальная редакция, порядок обновления и формат загрузки в pgvector.
6. **Telegram**: использовать встроенную интеграцию Hermes или отдельный бот через Telegram Bot API.
7. **Роли и права**: перечень ролей и матрица доступа (абитуриент, сотрудник приёмной комиссии, администратор и т.д.).
8. **Требования к хранению ПДн**: сроки хранения, состав данных, требования к защите.

## 13. Чего не делать

- Не писать собственную реализацию диалогового движка, планировщика агента или протокола MCP.
- Не добавлять ЕСИА и другие интеграции вне согласованного объёма.
- Не помещать бизнес-логику в промпты вместо кода и инструментов.
- Не хранить состояние сессий и бизнес-данные в SQLite — SQLite принадлежит Hermes.
- Не коммитить секреты, реальные ПДн и сгенерированные артефакты.
- Не менять работающие компоненты без причины и без проверки.
