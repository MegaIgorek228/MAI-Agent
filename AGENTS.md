# AGENTS.md

Инструкции для ИИ-агентов и разработчиков, работающих в этом репозитории.

## 1. О проекте

Проект — простой ИИ-агент для Московского авиационного института (МАИ) на базе **Hermes Agent**.

Текущая целевая архитектура (концепция от 2026-11-23, **sessionless**):

- **Пользовательских аккаунтов, профилей, ролей и JWT нет.** Единственная
  единица пользовательского контекста — **сессия Hermes**. Web и Telegram —
  тонкие поверхности, сопоставляемые с сессиями (`agent_sessions`).
- **Hermes Agent — единственный агент.** Вся логика, планирование, память
  (`MEMORY.md`), история диалога (`state.db`, восстановление через ACP
  `session/load`), терминал, файловая система и штатные инструменты —
  средствами самой Hermes. Собственные системы памяти/профилей поверх Hermes
  не создаются.
- **Backend — минимальный транспортный мост** (FastAPI): принимает сообщения из Web и
  Telegram, передаёт их Hermes через ACP (stdio) и возвращает ответы. Собственной
  агентной и предметной бизнес-логики не несёт.
- **Web** — простой чат с агентом (без кабинетов, профилей и заявлений).
- **Telegram** — простой чат с тем же агентом (polling живёт только в Backend).
- **Два источника данных** доступны агенту через MCP (встроен в Backend, FastMCP):
  1. имитация ФИС ГИА (синтетический реестр участников ЕГЭ — `synthetic_ege_*`);
  2. SQL-хранилище (read-only `sql_query`: официальные материалы приёма
     `knowledge_*`, данные приёмной кампании).

Ключевые принципы:
- не создавать новую агентную платформу поверх Hermes;
- не заменять ACP самодельным HTTP-протоколом;
- не создавать собственные инструменты, дублирующие штатные возможности Hermes,
  без доказанной необходимости;
- не добавлять инфраструктурные компоненты (Redis, очереди и т.п.) без необходимости.

## 2. Роль исполнителя

Выступай как ведущий Python-разработчик и архитектор ПО:
- работай небольшими проверяемыми этапами;
- перед существенными изменениями объясняй, что и зачем делаешь, какие файлы затрагиваешь и как проверишь результат;
- не переходи к следующему этапу, пока текущий не проверен;
- сообщай о нехватке документации или данных вместо того, чтобы придумывать решение.

Язык общения и документации — русский. Код, имена переменных, API и комментарии в коде — английский (если не оговорено иное).

## 3. Технологический стек

| Слой | Решение | Назначение |
| --- | --- | --- |
| Агент | Hermes Agent (пакет `hermes-agent`, ACP stdio) | Единственный агент: диалог, планирование, инструменты, память |
| Backend | Python + FastAPI | Транспорт Web/Telegram ↔ Hermes, MCP-хост, авторизация |
| Связь Backend ↔ Hermes | ACP (stdio) | Протокол `acp`, пул процессов `hermes-acp` |
| Инструменты агента | MCP + FastMCP | Имитация ФИС ГИА, read-only SQL, веб-страницы |
| LLM | DeepSeek (deepseek-v4.1-flash) через MAI relay | Модель Hermes (OpenAI-совместимый API) |
| Основная БД | PostgreSQL | Пользователи, сессии чата, источники данных |
| Состояние Hermes | SQLite в профиле Hermes | Внутреннее хранение сессий и памяти Hermes |
| Frontend | React + TypeScript | Простой чат с агентом |
| Telegram | Telegram Bot API (polling в Backend) | Чат с тем же агентом |
| Развёртывание | Docker Compose | `backend` + `frontend` + `postgres` |

## 4. Функциональные требования (текущая концепция)

1. Чат с агентом в Web: сообщения, история диалогов, отправка изображений (анализ
   нативным vision модели).
2. Чат с агентом в Telegram: те же возможности, тот же агент, отдельные сессии
   пользователей.
3. Доступ агента к штатным инструментам Hermes: терминал, файлы, выполнение кода,
   память `MEMORY.md`, поиск по истории сессий, планирование (`todo`).
4. Доступ агента к источникам данных через MCP: имитация ФИС ГИА и read-only SQL.
5. Разделение сессий: каждый пользователь (Web или Telegram) имеет собственную
   сессию Hermes; два канала не смешивают чужие диалоги.

Старая функциональность приёмной кампании (заявления, проверка документов,
кабинеты, роли) остаётся в коде до успешной проверки новой версии и явного решения
о её удалении — см. `docs/ARCHITECTURE.md`.

## 5. Архитектурные принципы

1. **Не дублируй готовое.** Если функциональность уже есть в Hermes, FastAPI, MCP/FastMCP, PostgreSQL или React — используй её.
2. **Минимум сервисов.** Базовый набор: backend (FastAPI + встроенный MCP), frontend (React), Hermes, PostgreSQL.
3. **Понятное назначение.** У каждого компонента и MCP-инструмента — одна ясная ответственность.
4. **Явные границы.** Backend не реализует логику диалога и планирования — это зона Hermes.
5. **Один источник истины.** Схема БД — миграции (Alembic); конфигурация — переменные окружения; API — OpenAPI FastAPI.
6. **Сначала проверка документации.** Перед выбором библиотеки или метода сверяйся с актуальной официальной документацией.

## 6. Правила разработки

1. Не реализуй самостоятельно то, что уже умеют Hermes, FastAPI или другие выбранные инструменты.
2. Перед установкой библиотеки проверяй её актуальную документацию и совместимость с остальным стеком.
3. Не придумывай API, методы, параметры и возможности библиотек. Сомневаешься — проверь документацию или спроси.
4. Не используй устаревшие методы и версии библиотек.
5. Не создавай лишние микросервисы.
6. Не усложняй архитектуру без необходимости.
7. Каждый компонент должен иметь понятное назначение.
8. После каждого этапа запускай доступные тесты и проверяй результат.
9. Не переходи к следующему этапу, пока текущий не проверен.
10. Не удаляй и не переписывай уже работающие компоненты без необходимости.
11. Не записывай секреты, пароли и API-ключи в исходный код.
12. Не используй реальные персональные данные абитуриентов при разработке.
13. При отсутствии документации или исходных данных сначала сообщай об этом, а не придумывай решение.

## 7. Порядок работы над этапом

Перед началом этапа:
1. Сформулировать цель этапа и критерии готовности.
2. Перечислить затрагиваемые файлы и компоненты.
3. Указать, как будет проверен результат (тесты, ручной сценарий, команда).

После завершения этапа:
1. Запустить доступные проверки (тесты, линтеры, сборку, миграции).
2. Показать результат проверок.
3. Кратко описать, что изменено и что осталось.
4. Только после этого предлагать следующий этап.

Статус этапов и принятые решения фиксируются в `docs/`.

## 8. Проверки качества

- тесты backend — `pytest` (из `backend/`: `python -m pytest ../tests -q`);
- сквозной E2E новой архитектуры — `python scripts/e2e_minimal_agent.py` (нужен запущенный стек);
- проверка типов и сборка frontend — `tsc` + Vite (выполняются в Docker-сборке образа);
- миграции БД — только через Alembic;
- `docker compose up -d` поднимает стек целиком без ручных шагов (см. `docs/DEPLOYMENT.md`).

Правило: этап не считается завершённым, если проверки не запускались или падают без объяснения причины.

## 9. Безопасность и данные

1. Секреты (пароли БД, токены ботов, ключи API) хранятся только в переменных окружения. В репозитории — `.env.example` с фиктивными значениями.
2. В репозиторий не попадают `.env`, дампы БД, загруженные документы, логи.
3. Данные в тестах — только синтетические.
4. Доступ к данным — с проверкой на backend. MCP-инструменты проверяют доверенный контекст пользователя (заголовок `x-mai-context`).
5. `sql_query` — строго read-only: одна SELECT/WITH-команда, лимит строк, без таблиц учётных записей (`users`, `staff_invites`).
6. Персональные данные не передаются в LLM сверх необходимого минимума.

## 10. Работа с библиотеками и зависимостями

1. Версии фиксируются в `backend/pyproject.toml` (uv-совместимо) и в сборке образа.
2. Новые зависимости добавляются только с обоснованием.
3. Перед добавлением проверяется актуальная версия и совместимость со стеком.
4. Не используются заброшенные пакеты, если есть поддерживаемая альтернатива.

## 12. Чего не делать

- Не писать собственную реализацию диалогового движка, планировщика агента или протокола MCP/ACP.
- Не добавлять ЕСИА и другие интеграции вне согласованного объёма.
- Не создавать инструменты, дублирующие штатные возможности Hermes, без доказанной необходимости.
- Не помещать бизнес-логику в промпты вместо кода и инструментов.
- Не хранить бизнес-данные в SQLite — SQLite принадлежит Hermes; данные — в PostgreSQL.
- Не коммитить секреты, реальные ПДн и сгенерированные артефакты.
- Не менять master и не выполнять merge без явного разрешения владельца.
- Не останавливать/перезапускать основные gateway-процессы Hermes на хосте без явного разрешения.
