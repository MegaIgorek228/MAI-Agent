# Целевая архитектура MAI-Agent

## Статус документа

Это окончательный черновик архитектуры для последующей реализации. Документ основан на [AGENTS.md](../AGENTS.md), [README.md](../README.md), [TECHNICAL_DECISIONS.md](TECHNICAL_DECISIONS.md) и ранее проведённом исследовании технологий.

В документе явно разделены:

- **принятые решения** — обязательные ограничения текущего проекта;
- **предварительные решения** — предпочтительный вариант, требующий проверки;
- **нерешённые вопросы** — темы, по которым нельзя делать предположения до проверки документации или эксперимента.

Документ не фиксирует версии библиотек, конкретную модель Qwen, неподтверждённые API и параметры конфигурации.

## Общая архитектура

MAI-Agent состоит из центрального Backend на FastAPI, агентной среды Hermes Agent, ограниченного набора MCP-инструментов, PostgreSQL с pgvector и web-интерфейса на React + TypeScript.

Принципиальная схема:

```text
Пользователь
   │
   ├── Web ────────────────┐
   │                       │
   └── Telegram Gateway ───┤
                           ▼
                    FastAPI Backend
                    │     │      │
                    │     │      └── PostgreSQL + pgvector
                    │     │
                    │     └── MCP/FastMCP tools
                    │
                    └── ACP (исследуемый транспорт: stdio)
                                  │
                                  ▼
                           Hermes Agent
                                  │
                                  └── Qwen через поддерживаемый
                                      Hermes inference provider
```

### Принятые решения

1. FastAPI остаётся центральным Backend проекта.
2. ACP является обязательным протоколом взаимодействия Backend с Hermes.
3. Основной исследуемый транспорт ACP — stdio.
4. Hermes отвечает за диалог, планирование и выбор инструментов.
5. Backend отвечает за бизнес-логику, пользователей, роли, авторизацию и интеграции.
6. PostgreSQL является основной базой бизнес-данных и истории приложения.
7. SQLite используется только Hermes для его внутреннего состояния и сессий агента.
8. Дополнительные сервисы, включая Redis и RabbitMQ, не добавляются без доказанной необходимости.

### Предварительные решения

1. MCP/FastMCP на первом этапе размещается внутри Backend, если это совместимо с зависимостями и жизненным циклом приложений.
2. Telegram Gateway Hermes является предпочтительным Telegram-вариантом.
3. Резервный Telegram-вариант — Telegram Bot API, подключённый внутри Backend.
4. Qwen подключается через поддерживаемый Hermes inference provider.
5. Конкретная модель Qwen и способ её запуска пока не фиксируются.

## Компоненты и их ответственность

### FastAPI Backend

Backend предоставляет:

- HTTP API для frontend и каналов доступа;
- аутентификацию и авторизацию;
- управление пользователями, ролями и профилями;
- работу с документами и их статусами;
- бизнес-правила проверки комплектности документов;
- интеграционные адаптеры;
- хранение истории приложения и аудита;
- ACP-клиент для Hermes;
- MCP-инструменты, если их размещение внутри Backend подтвердит совместимость.

Backend является источником истины для ролей, прав доступа и бизнес-данных.

Backend не реализует собственный диалоговый движок и планировщик.

### Hermes Agent

Hermes предоставляет готовую агентную среду для:

- ведения диалога;
- планирования;
- вызова разрешённых MCP-инструментов;
- работы с моделью Qwen;
- хранения внутреннего состояния и сессий агента в SQLite.

Hermes не должен:

- иметь произвольный доступ к терминалу;
- иметь произвольный доступ к файловой системе;
- подключаться к PostgreSQL напрямую;
- самостоятельно принимать решения о правах пользователя;
- получать инструменты, не относящиеся к функциям MAI-Agent.

Набор инструментов Hermes должен быть минимальным, явно перечисленным и ограниченным политиками доступа.

### ACP

ACP используется как обязательная граница Backend ↔ Hermes.

На первом этапе проверяется схема:

```text
FastAPI Backend
      │
      │ ACP client
      │ stdio
      ▼
Hermes ACP adapter
      │
      ▼
Hermes Agent
```

ACP-клиент Backend должен отвечать за:

- создание сессии агента;
- передачу пользовательского запроса;
- получение ответа и потоковых событий;
- отмену выполнения;
- продолжение сессии;
- обработку ошибок и завершения процесса.

Поддержка удалённого ACP через HTTP или WebSocket не считается подтверждённой и не используется как исходное допущение.

### MCP/FastMCP

MCP-инструменты предоставляют Hermes строго ограниченный доступ к операциям MAI-Agent.

На первом этапе предпочтительно разместить MCP/FastMCP внутри Backend. Это уменьшает число сервисов и позволяет использовать общие:

- модели данных;
- проверки авторизации;
- транзакции;
- журналы аудита;
- конфигурацию.

Отдельный `mcp_server` создаётся только если:

- зависимости FastMCP конфликтуют с Backend;
- требуется независимый жизненный цикл;
- появляется отдельная граница безопасности;
- официальная документация или эксперимент подтверждают необходимость разделения.

MCP-инструменты не должны предоставлять Hermes произвольный SQL, shell, файловый доступ или доступ к внутренним секретам.

### PostgreSQL и pgvector

PostgreSQL хранит:

- пользователей;
- роли;
- профили абитуриентов;
- связи с внешними каналами;
- метаданные документов;
- результаты проверки документов;
- бизнес-историю приложения;
- аудит;
- подготовленные фрагменты нормативных документов;
- embeddings для семантического поиска.

pgvector используется для поиска по правилам приёма и другим согласованным нормативным материалам.

Конкретные embedding-модель, размерность и тип индекса пока не зафиксированы.

### React + TypeScript

Frontend предоставляет:

- web-интерфейс абитуриента;
- интерфейс сотрудника приёмной комиссии;
- формы и отображение профиля;
- загрузку и просмотр статусов документов;
- диалоговый интерфейс;
- отображение результатов Backend API.

Frontend не обращается напрямую к PostgreSQL, Hermes или MCP и не является источником решений об авторизации.

## Взаимодействие компонентов

### Web-сценарий

1. Пользователь взаимодействует с React-приложением.
2. Frontend отправляет запрос в FastAPI Backend.
3. Backend аутентифицирует пользователя и проверяет его роль.
4. Для диалогового запроса Backend создаёт или продолжает ACP-сессию Hermes.
5. Hermes обрабатывает запрос и при необходимости вызывает разрешённый MCP-инструмент.
6. MCP-инструмент выполняет только разрешённую операцию через Backend.
7. Backend обращается к PostgreSQL и возвращает результат инструмента.
8. Hermes формирует ответ.
9. Backend возвращает ответ frontend.

### MCP-контекст

Hermes не должен самостоятельно формировать доверенный идентификатор пользователя.

Предпочтительная схема:

1. Backend определяет пользователя и его права.
2. Backend формирует ограниченный контекст запроса.
3. MCP-инструмент проверяет контекст и срок его действия.
4. Backend повторно проверяет права перед чувствительной операцией.
5. Результат и факт обращения записываются в аудит без лишних персональных данных.

Механизм подписи и формат контекста требуют отдельного решения после проверки требований безопасности.

### Сессии

Разделяются два вида состояния:

- **сессия агента** — внутреннее состояние Hermes в SQLite;
- **сессия приложения** — пользователь, канал, роли, связь с Hermes-сессией и бизнес-аудит в PostgreSQL.

Точный механизм сопоставления ACP-сессии с пользователем приложения должен быть проверен на прототипе.

## Хранение данных

| Данные | Хранилище | Ответственный |
|---|---|---|
| Пользователи и роли | PostgreSQL | Backend |
| Профили абитуриентов | PostgreSQL | Backend |
| Метаданные документов | PostgreSQL | Backend |
| История приложения | PostgreSQL | Backend |
| Аудит действий | PostgreSQL | Backend |
| Фрагменты документов | PostgreSQL или согласованное хранилище | Backend |
| Embeddings | PostgreSQL + pgvector | Backend/ingestion |
| Внутренние сессии агента | SQLite Hermes | Hermes |
| Секреты | Переменные окружения/секретное хранилище | Среда запуска |

Нельзя хранить бизнес-данные пользователей и историю приложения в SQLite Hermes.

Перед передачей данных в Qwen необходимо определить минимально допустимый состав персональных данных.

## Авторизация и безопасность

### Backend authorization

Все решения о доступе принимаются Backend. Frontend и Hermes не могут заменять серверную авторизацию.

Предварительно предусматриваются роли:

- абитуриент;
- сотрудник приёмной комиссии;
- администратор.

Окончательная матрица ролей и разрешений ещё не утверждена.

### Инструменты Hermes

Инструменты следует разделить на:

- операции чтения;
- операции с персональными данными;
- изменяющие операции;
- административные операции.

По умолчанию Hermes получает только минимальный набор read-only инструментов. Изменяющие операции требуют отдельной авторизации, аудита и проверки идемпотентности.

### Защита секретов

В Git и исходном коде не хранятся:

- токены Telegram;
- ключи Qwen или inference provider;
- пароли PostgreSQL;
- ключи ACP/API Server;
- ключи подписи пользовательского контекста.

### Персональные данные

До реализации необходимо определить:

- состав и классификацию персональных данных;
- сроки хранения;
- правила удаления;
- доступ сотрудников;
- допустимый объём передачи в Hermes и Qwen;
- требования к аудиту;
- правила обезличивания тестовых данных.

## Telegram

### Предпочтительный вариант

Использовать встроенный Hermes Telegram Gateway, если эксперимент подтвердит:

- совместимость с ACP-архитектурой;
- корректное сопоставление Telegram-пользователя с пользователем Backend;
- передачу необходимого пользовательского контекста;
- соблюдение ролей и прав Backend;
- отсутствие прямого обхода бизнес-логики Backend.

Такой вариант не создаёт дополнительный Telegram-сервис и использует готовую возможность Hermes.

### Резервный вариант

Если Gateway не удовлетворяет требованиям, Telegram Bot API подключается внутри Backend как тонкий канал доступа. В этом случае Backend:

- принимает сообщения Telegram;
- идентифицирует пользователя;
- применяет авторизацию;
- передаёт запрос Hermes через ACP;
- возвращает ответ в Telegram.

Отдельный Telegram-микросервис не создаётся.

Совместимость Gateway с выбранной моделью авторизации и ACP пока не подтверждена.

## Docker Compose

Минимальный целевой состав:

```text
backend
hermes
postgres
frontend
```

FastMCP размещается внутри `backend`, если зависимости совместимы.

Отдельный `mcp_server` добавляется только при доказанной необходимости. Telegram Gateway размещается внутри Hermes, если выбран этот вариант интеграции.

Docker Compose должен обеспечить:

- отдельную внутреннюю сеть;
- persistent volume PostgreSQL;
- persistent volume SQLite Hermes;
- передачу секретов через окружение;
- healthchecks;
- отсутствие внешней публикации PostgreSQL без необходимости.

Не добавляются Redis, RabbitMQ, отдельная vector database, отдельный Telegram-сервис или дополнительные worker-сервисы без подтверждённой потребности.

Нужно отдельно проверить наличие официального Docker image Hermes и требования к GPU для выбранного inference provider.

## Нерешённые технические вопросы

1. Точная версия и способ установки Hermes.
2. Реальное поведение Hermes ACP adapter.
3. Жизненный цикл ACP stdio-сессий.
4. Создание, продолжение и восстановление сессий.
5. Поддержка нескольких одновременных пользователей.
6. Совместимость FastMCP с размещением внутри FastAPI.
7. Формат и защита доверенного MCP-контекста.
8. Совместимость Hermes Telegram Gateway с Backend authorization и ACP.
9. Конкретная модель Qwen.
10. Способ запуска Qwen через Hermes inference provider.
11. Требования к CPU/GPU и Docker deployment.
12. Embedding-модель, размерность и индекс pgvector.
13. Политика хранения истории диалогов.
14. Требования к хранению документов и персональных данных.
15. Официальная документация и разрешённый доступ к ФИС ГИА.
16. Точный состав ролей и матрица разрешений.

ФИС ГИА не реализуется до получения официальной документации, схемы авторизации и разрешённого доступа к тестовому или рабочему контуру.

## Последовательность реализации

### Этап 1. Зафиксировать версии и границы

- выбрать версии Hermes, ACP, Python, FastAPI, FastMCP и PostgreSQL;
- определить формат конфигурации;
- подтвердить отсутствие необходимости в дополнительных сервисах.

### Этап 2. Провести ACP-прототип

- запустить Hermes ACP;
- выполнить инициализацию;
- создать сессию;
- отправить запрос;
- получить ответ и потоковые события;
- отменить и продолжить сессию;
- проверить восстановление после перезапуска Backend.

### Этап 3. Проверить размещение MCP внутри Backend

- подключить минимальный read-only инструмент;
- проверить совместимость зависимостей;
- проверить изоляцию и обработку ошибок;
- проверить передачу доверенного контекста.

### Этап 4. Создать Backend foundation

- конфигурация;
- health endpoint;
- пользователи и роли;
- ACP orchestration;
- OpenAPI-контракт;
- аудит.

### Этап 5. Спроектировать PostgreSQL

- миграции;
- пользователи и роли;
- профили;
- документы;
- история приложения;
- аудит;
- подготовка pgvector.

### Этап 6. Добавить ограниченные MCP-инструменты

Начать с безопасных операций чтения. Изменяющие операции добавлять только после завершения проверки авторизации и аудита.

### Этап 7. Проверить Telegram Gateway

Проверить идентификацию, права, ACP-маршрутизацию и связь с Backend. При невозможности гарантировать эти свойства использовать резервный Backend adapter через Telegram Bot API.

### Этап 8. Реализовать Frontend

Подключить React + TypeScript только к публичному Backend API.

### Этап 9. Подключить Qwen

Выбрать модель и inference provider после измерения требований к ресурсам, tool calling и защите данных.

### Этап 10. Реализовать поиск

После выбора embedding-модели включить pgvector, определить размерность и стратегию индексации.

### Этап 11. ФИС ГИА

Начать интеграцию только после получения официальной документации и разрешённого доступа.

### Этап 12. Docker Compose и проверки

Добавить Compose-конфигурацию, persistent volumes, healthchecks, тестовые сценарии и проверки качества.
